# Contributing

Every change to Lentil follows these standards. What Lentil does is defined in the [PRD](docs/PRD.md), and how clients share a repository in the [convention spec](docs/SPEC.md).

| Area | Requirement |
| --- | --- |
| Testing | Finance logic is covered by unit tests, differential tests against the reference implementation and mutation tests with cargo-mutants; the mutation tests are the actual quality gate, and at least 80 % line coverage for `lentil-core`, measured with cargo-llvm-cov, is a floor. Finance logic lives only in `lentil-core`; the Android app holds none and is covered by unit tests of its view models and by UI tests in an emulator. Multi-writer sync tests simulate several clients pushing to one repository and fail on lost intents, duplicates or non-linear history; property-based tests cover replay. cargo-nextest runs the Rust tests, and `cargo test --doc` runs the doc tests, which nextest skips. All run before every merge, alongside agent reviews. Test dependencies are dev-only and never ship. |
| Static analysis | Rust: clippy over all targets with warnings as errors and selected pedantic lints, configured once in `[workspace.lints]` of the root `Cargo.toml`; rustfmt with its default settings. Kotlin: Android Lint and detekt with warnings as errors, ktfmt. A frontend linter only if a web UI is built. |
| Architecture | Traits, or interfaces in Kotlin, only at I/O boundaries (Git, file system, clock, randomness, import sources); business logic such as replay, ID generation and validation stays in pure functions. Tests replace these boundaries with fakes, not with a mocking library. Git runs inside `lentil-core`, so the CLI and the Android app share one implementation of synchronization. The Android app keeps its pending intents in its own storage and hands them to the core for replay, and it wires its dependencies by hand, without a dependency injection framework. The core reports validation findings and conflicts as typed codes, not as English text, and each client translates them. |
| Dependencies | Every new direct dependency is justified in its pull request. cargo-deny checks licenses, duplicate versions and advisories and admits crates.io as the only source; any other source needs an explicit exception in its configuration. CI checks the licenses of the Gradle dependencies against the same license allowlist, and cargo-machete reports unused Rust dependencies. rustledger is pinned to an exact version and upgraded deliberately, guarded by the differential tests. UniFFI is pinned exactly as well, because its runtime crate and the generated bindings must match. Direct dependencies are upgraded on the project's own schedule; transitive ones change only when a direct dependency requires it or to fix a vulnerability that affects Lentil. |
| Vulnerability scanning | Daily osv-scanner over `Cargo.lock` and the Gradle lockfiles, on `main` and on the latest release; Grype on container images once there are any. A weekly CI run tests against the newest direct dependencies. No update bots; Dependabot only bumps the SHA-pinned GitHub Actions. |
| Build | Each language uses its native build tool: a Cargo workspace for `lentil-core` and the CLI, Gradle with the Kotlin DSL and a version catalog for the Android app, which embeds the core built by Cargo. A task in the `build-logic` convention plugins runs cargo-ndk for each Android ABI through the Android Gradle Plugin's current Variant API, without a third-party Rust plugin. UniFFI generates the Kotlin bindings during the build with a `uniffi-bindgen` built from the Cargo workspace, so no extra tool needs installing. There is no cross-language build system such as Bazel. The Nix flake's development shell pins every toolchain and tool, including the cargo subcommands and Python Beancount for the differential tests, and is used both locally and in CI. The flake packages the CLI with crane. Rust and the NDK are pinned only in `rust-toolchain.toml`, which also lists the Rust components and targets, and in the Gradle build's `ndkVersion`. The shell reads both, Rust through rust-overlay, so rust-analyzer matches the compiler and F-Droid builds with the same versions. The builds themselves do not require that shell: F-Droid rebuilds the APK on its own build servers, so the Gradle build finds its toolchains through the usual environment and never through hard-coded or Nix store paths, and Gradle never downloads a JDK itself. Because the aapt2 that the Android Gradle Plugin fetches from Maven does not run on NixOS, the development shell points the plugin to the SDK's aapt2 through an environment variable. |
| CI and hosting | GitHub, with GitHub Actions. Every action is pinned by commit SHA. |
| Releases | SemVer for releases. Compatibility between clients is governed by `spec_version`, not by the app version. Android additionally uses an increasing `versionCode`. The crates are not published on crates.io; the workspace sets `publish = false`. Release artifacts are built with Rust's native tooling, cargo for each target in GitHub Actions. Checksums, SBOMs, signatures and the GitHub release are separate workflow steps. |
| Supply chain | An SBOM for every release artifact. CLI binaries are signed with cosign keyless signing through GitHub OIDC, so no long-lived signing key exists for them; the same applies to container images once there are any. The Android APK is built reproducibly, so F-Droid can publish the developer-signed APK; CI checks this by building it twice in different paths and comparing the results. The Rust libraries in it are built with `--remap-path-prefix`, so they contain no build paths. The APK omits the dependency information block that the Android Gradle Plugin adds to the signing block by default, because only Google Play can read it. Gradle verifies the checksums of its wrapper distribution and of every dependency. |
