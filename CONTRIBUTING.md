# Contributing

Every change to Lentil follows these standards. What Lentil does is defined in the [PRD](docs/PRD.md), and how clients share a repository in the [convention spec](docs/SPEC.md).

| Area | Requirement |
| --- | --- |
| Testing | Finance logic is covered by unit tests, differential tests against the reference implementation and mutation tests with cargo-mutants; the mutation tests are the actual quality gate, and at least 80 % line coverage for `lentil-core`, measured with cargo-llvm-cov, is a floor. On every change to `lentil-core`, CI mutates the changed lines and fails if the tests miss any of these mutants ([`scripts/mutation.sh`](scripts/mutation.sh), [`.cargo/mutants.toml`](.cargo/mutants.toml)); an equivalent mutant, which no test can catch, goes into `exclude_re` in `.cargo/mutants.toml` with its reason. Locally, `scripts/mutation.sh` without a ref mutates all of `lentil-core` and fails if test efficacy, the share of the viable mutants that the tests catch, drops below 85 %. Finance logic lives only in `lentil-core`; the Android app holds none and is covered by unit tests of its view models and by UI tests in an emulator. Multi-writer sync tests simulate several clients pushing to one repository and fail on lost intents, duplicates or non-linear history; property-based tests cover replay. cargo-nextest runs the Rust tests, and `cargo test --doc` runs the doc tests, which nextest skips. All run before every merge, alongside agent reviews. Test dependencies are dev-only and never ship. |
| Static analysis | Rust: clippy over all targets with warnings as errors and selected pedantic lints, configured once in `[workspace.lints]` of the root `Cargo.toml`; rustfmt with its default settings. Kotlin: Android Lint and detekt with warnings as errors, ktfmt. CodeQL scans the Rust code and the GitHub workflows on every change and weekly. A frontend linter only if a web UI is built. |
| Architecture | Traits, or interfaces in Kotlin, only at I/O boundaries (Git, file system, clock, randomness, import sources); business logic such as replay, ID generation and validation stays in pure functions. Tests replace these boundaries with fakes, not with a mocking library. Git runs inside `lentil-core`, so the CLI and the Android app share one implementation of synchronization. The Android app keeps its pending intents in its own storage and hands them to the core for replay, and it wires its dependencies by hand, without a dependency injection framework. The core reports validation findings and conflicts as typed codes, not as English text, and each client translates them. |
| Dependencies | Every new direct dependency is justified in its pull request. cargo-deny checks licenses, duplicate versions and, for the crates that ship, advisories, and admits crates.io as the only source; any other source needs an explicit exception in its configuration. On every pull request and push to `main`, GitHub's dependency review checks the Rust, Python and GitHub Actions dependencies that a change adds or updates: any known vulnerability fails, and so does a license outside the same allowlist, except for Python Beancount, Fava and their dependencies, which never ship and are exempted by name. A task in the `build-logic` convention plugins checks the licenses that the POMs of the app's runtime and test dependencies declare against the same allowlist, read from `deny.toml`; a POM that lists several licenses offers a choice between them, and JUnit, which only runs the tests, is exempt. cargo-machete reports unused Rust dependencies. rustledger is pinned to an exact version and upgraded deliberately, guarded by the differential tests. UniFFI is pinned exactly as well, because its runtime crate and the generated bindings must match. Direct dependencies are upgraded on the project's own schedule with [`scripts/deps.sh`](scripts/deps.sh); transitive ones change only when a direct dependency requires it or to fix a vulnerability that affects Lentil. |
| Vulnerability scanning | Only precise signals fail a scan ([`scripts/scan.sh`](scripts/scan.sh)). Vulnerabilities count in what ships, because they need attacker input, and build, lint and test tools only process Lentil's own code: cargo-deny checks the advisories of the crates without their dev-dependencies on every change and daily, and osv-scanner checks the app's `releaseRuntimeClasspath` whenever a lockfile changes and daily. Known malware counts in every package, because it does harm wherever it runs, on developer machines and in CI too: osv-scanner checks every lockfile whenever one changes and daily, dev-dependencies, Python Beancount and every artifact that Gradle downloads included. `scan.yml` scans `main`, and `scan-release.yml` scans the lockfiles of the latest release daily, with the ignores of `main`. The dependency review stays stricter, because it sees only what a change adds. Grype on container images once there are any. Every week, `latest-deps.yml` tests against the newest direct dependencies, the exact pins included. No update bots; Dependabot only bumps the SHA-pinned GitHub Actions, monthly in one pull request. |
| Build | Each language uses its native build tool: a Cargo workspace for `lentil-core` and the CLI, Gradle with the Kotlin DSL and a version catalog for the Android app, which embeds the core built by Cargo. A task in the `build-logic` convention plugins runs cargo-ndk for each Android ABI through the Android Gradle Plugin's current Variant API, without a third-party Rust plugin. UniFFI generates the Kotlin bindings during the build with a `uniffi-bindgen` built from the Cargo workspace, so no extra tool needs installing. There is no cross-language build system such as Bazel. The Nix flake's development shell pins every toolchain and tool, including the cargo subcommands, Python and uv, and is used both locally and in CI. uv installs Python Beancount for the differential tests, pinned exactly in `pyproject.toml` and `uv.lock`, and only ever uses the shell's Python, whose minor version `requires-python` pins as well. Fava, for viewing the example ledger, is pinned the same way in a dependency group of its own, so the tests never install it. The flake packages the CLI with crane. Rust and the NDK are pinned only in `rust-toolchain.toml`, which also lists the Rust components and targets, and in the Gradle build's `ndkVersion`. The shell reads both, Rust through rust-overlay, so rust-analyzer matches the compiler and F-Droid builds with the same versions. The builds themselves do not require that shell: F-Droid rebuilds the APK on its own build servers, so the Gradle build finds its toolchains through the usual environment and never through hard-coded or Nix store paths, and Gradle never downloads a JDK itself. Because the aapt2 that the Android Gradle Plugin fetches from Maven does not run on NixOS, the development shell points the plugin to the SDK's aapt2 through an environment variable. |
| CI and hosting | GitHub, with GitHub Actions. CI runs the recipes of the `justfile` inside the development shell, so `just <recipe>` runs locally what CI runs. Every action is pinned by commit SHA, and every job has a timeout. Changes that touch only documentation skip CI. |
| Releases | SemVer for releases. Compatibility between clients is governed by `spec_version`, not by the app version. Android additionally uses an increasing `versionCode`. The crates are not published on crates.io; the workspace sets `publish = false`. Release artifacts are built with Rust's native tooling, cargo for each target in GitHub Actions. Checksums, SBOMs, signatures and the GitHub release are separate workflow steps. |
| Supply chain | An SBOM for every release artifact. CLI binaries are signed with cosign keyless signing through GitHub OIDC, so no long-lived signing key exists for them; the same applies to container images once there are any. The Android APK is built reproducibly, so F-Droid can publish the developer-signed APK; CI checks this by building it twice in different paths and comparing the results. The Rust libraries in it are built with `--remap-path-prefix`, so they contain no build paths. The APK omits the dependency information block that the Android Gradle Plugin adds to the signing block by default, because only Google Play can read it. Gradle verifies the checksums of its wrapper distribution and of every dependency. |

## Updating dependencies

Direct dependencies are upgraded on the project's own schedule with [`scripts/deps.sh`](scripts/deps.sh), and the result goes into one `deps:` commit.

- `scripts/deps.sh upgrade` raises every direct crate to the newest version its requirement allows, and every version in the Gradle catalog except the Android toolchain to the newest stable release of its major. It then rewrites the Gradle verification metadata and lockfiles from an empty Gradle user home, which builds, tests and lints the app. Run the other checks of CI afterwards.
- Only direct dependencies are upgraded. A transitive dependency changes only where an upgraded direct dependency requires it, or to fix a vulnerability (see below). The script updates conservatively with `cargo update -p <crate>` and `uv lock --upgrade-package <package>`; `cargo update` or `uv lock --upgrade` without a package would rewrite every transitive version.
- The exact pins are upgraded deliberately: `scripts/deps.sh upgrade pins` raises rustledger, UniFFI, Beancount and Fava to their newest release. The differential tests guard rustledger and Beancount, and the app build guards UniFFI's generated bindings; nothing tests Fava, which only shows the example ledger. Fava requires Beancount below 4 and shares the lock with it, so the pins stay on Beancount 3 until a Fava release allows 4; a note in `pyproject.toml` says so.
- Major versions, the Gradle wrapper, the Android SDK and NDK, the Rust toolchain, the JDK, Python and the flake inputs stay manual steps. `scripts/deps.sh outdated` lists them for review, together with every direct dependency that has a newer release and the notes in code and configuration that wait for an event. Such a note says "Revisit" or "Drop this once", so that the list finds it.
- `latest-deps.yml` runs all three upgrades every week in a gVisor sandbox without the job's token and tests the result. It commits nothing, so a failure means that the next upgrade needs work. It also puts the list of `scripts/deps.sh outdated` into its summary, which never fails.

## When a vulnerability scan fails

Handle a finding like a reported vulnerability: assess it, fix it through the direct dependency, and ignore it only with a reason.

1. Assess the impact. A finding in `scan-release.yml` concerns what users run; if `scan.yml` no longer reports it, the fix is already on `main` and only needs a release.
2. Fix it by upgrading the direct dependency. If the vulnerable package is transitive and no fixed version of the direct dependency exists yet, raise only that package, to the fixed version and not to the latest (`cargo update -p <crate> --precise <version>`, or a dependency constraint in the app's Gradle build), and report it upstream. Drop the constraint once the direct dependency ships the fix.
3. If users are affected, cut a patch release and publish a GitHub Security Advisory.
4. Only if the finding does not apply to Lentil, ignore it with its reason: in `[advisories]` of `deny.toml` for a crate, as an `[[IgnoredVulns]]` entry in `osv-scanner.toml` for a Gradle package. An ignore in `deny.toml` that no longer matches fails the check, so it goes once it is obsolete.

## When the malware check fails

Known malware is an incident, not an upgrade: find out where the package ran before removing it.

1. Find out since when the version is in the lockfile (`git log -S '<package>' -- <lockfile>`) and which machines built or installed it since, developer machines and CI runners alike.
2. Rotate every credential those machines could reach: Git and GitHub tokens, SSH keys and the key that signs the APK.
3. Check the releases built since then. If one may be affected, publish a GitHub Security Advisory and cut a clean release.
4. Remove the version: upgrade or downgrade the direct dependency, or raise the transitive one to a clean version, as in the exception above.
